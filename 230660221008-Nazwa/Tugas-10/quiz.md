Soal 1 — Integrasi Data. Integrasi data pada aplikasi mobile adalah proses menghubungkan dan menyatukan data dari beberapa sumber layanan (endpoint REST API) yang terpisah agar dapat disajikan sebagai satu alur proses bisnis yang utuh pada antarmuka pengguna. Secara teknis, basis data relasional pada backend Sistem Informasi memisahkan entitas ke dalam tabel dan endpoint yang berbeda untuk menjaga normalisasi data, sehingga lapisan service pada aplikasi mobile harus menggabungkan relasi data tersebut sebelum ditampilkan ke layar. Contoh pada Proses Bisnis Sistem Informasi (Pengaduan Fasilitas Kampus): Ketika mahasiswa atau petugas membuka halaman daftar pengaduan, aplikasi mengambil rincian laporan kerusakan dari endpoint pengaduan (GET /posts), mengambil nama mahasiswa pelapor dari endpoint pengguna (GET /users), dan mengambil informasi lokasi gedung/ruang dari endpoint fasilitas (GET /comments sebagai simulasi).   Identifier Penghubung: Data antar-endpoint tersebut dihubungkan menggunakan userId (mencocokkan field userId pada objek pengaduan dengan id pada objek pengguna) serta roomId / fasilitasId (mencocokkan lokasi fasilitas kampus yang dilaporkan).   
Soal 2 — Future.wait. Kapan Future.wait digunakan: Future.wait digunakan ketika aplikasi perlu menjalankan beberapa pemanggilan API (asynchronous request) secara paralel (bersamaan) karena request-request tersebut tidak saling bergantung satu sama lain. Alasan teknisnya adalah efisiensi latensi jaringan: total waktu tunggu muat halaman hanya sepanjang waktu eksekusi request yang paling lambat, bukan penjumlahan waktu dari seluruh request. Pada project Pengaduan Fasilitas Kampus, request ambilPengguna() (GET /users) dan ambilDaftarPengaduan() (GET /posts) dijalankan bersamaan melalui Future.wait sebelum digabungkan berdasarkan userId. Kondisi yang mengharuskan request berjalan berurutan: Request wajib dieksekusi secara berurutan (sequential dengan await satu per satu) apabila request kedua membutuhkan parameter atau identifier yang baru diperoleh dari hasil respons request pertama. Contohnya, jika aplikasi membuka halaman detail laporan tertentu terlebih dahulu untuk mendapatkan nilai userId pelapor dari server, barulah aplikasi dapat mengeksekusi request kedua ke endpoint /users/{userId} untuk mengambil profil lengkap pelapor tersebut.   
Soal 3 — Model dan fromJson. Field yang dibutuhkan model DataPengajuan: Untuk menghubungkan data pengguna, lokasi fasilitas, dan pengajuan laporan pada project Pengaduan Fasilitas Kampus, model DataPengajuan memerlukan field berikut:id (int / String): Primary key unik untuk setiap data pengajuan laporan.   userId (int): Foreign key yang menghubungkan laporan pengaduan dengan pemilik akun pada model DataPengguna.   roomId (int): Foreign key yang menghubungkan laporan dengan lokasi ruangan/fasilitas pada model DataRuang.   Field atribut proses bisnis seperti fasilitas / judul (String), kendala (String), dan status (String, seperti menunggu, diproses, atau selesai).   Cara fromJson menangani field yang tidak tersedia: Di dalam factory DataPengajuan.fromJson(Map<String, dynamic> json), setiap nilai dari Map JSON dibaca menggunakan pengecekan tipe nullable (as String? atau as int?) yang dipadukan dengan null-coalescing operator (??) untuk memberikan nilai default. Contohnya: status: json['status'] as String? ?? 'menunggu' atau roomId: json['roomId'] as int? ?? 1. Secara teknis, mekanisme ini mencegah terjadinya runtime crash (TypeError: type 'Null' is not a subtype of type ...) ketika struktur JSON dari API simulasi belum menyediakan kolom spesifik domain Sistem Informasi.   
Soal 4 — Service Layer. Perbandingan Tanggung Jawab:Service Layer (IntegrasiService): Bertanggung jawab penuh atas komunikasi HTTP ke berbagai endpoint (http.get), eksekusi paralel (Future.wait), validasi HTTP statusCode dan timeout, deserialisasi JSON mentah (jsonDecode) menjadi objek model Dart (fromJson), penggabungan data antar-model menggunakan userId, serta penerapan aturan proses bisnis (seperti pemetaan status pengajuan) sebelum mengembalikan model ringkas ke pemanggil.   Widget (Halaman Flutter): Bertanggung jawab murni mengelola UI state (_sedangMemuat, _pesanError, _daftarPengaduan), memicu pemanggilan method service (pada initState atau tombol Coba Lagi), dan merender tampilan antarmuka berdasarkan state tersebut.   Mengapa penggabungan data tidak boleh ditulis langsung di dalam widget: Method build() pada widget Flutter dapat dieksekusi berulang kali secara cepat setiap terjadi pembaruan frame atau pemanggilan setState(). Jika logika HTTP dan iterasi penggabungan data diletakkan di dalam widget, aplikasi berisiko memicu pemanggilan jaringan berulang tanpa kendali, membebani UI thread hingga tampilan patah-patah (jank), merusak pemisahan tanggung jawab (Separation of Concerns), serta membuat kode sulit diuji maupun disesuaikan apabila struktur API backend berubah.   
Soal 5 — Status Halaman. State yang perlu ditangani halaman integrasi data: Halaman wajib membedakan empat kondisi antarmuka: 1. Loading (_sedangMemuat = true): Menampilkan indikator pemrosesan (CircularProgressIndicator) selama Future.wait menunggu respons dari seluruh endpoint. 2. Data Berhasil Dimuat (_daftar.isNotEmpty): Menampilkan daftar pengaduan terintegrasi (nama pelapor, ruang/fasilitas, dan status) menggunakan ListView.builder. 3. Data Kosong (_daftar.isEmpty tanpa error): Menampilkan pesan informatif (misalnya "Belum ada laporan pengaduan fasilitas") ketika server merespons sukses namun daftar datanya kosong. 4. Error Request (_pesanError != null): Menampilkan pesan kesalahan yang mudah dipahami pengguna beserta tombol Coba Lagi ketika terjadi kegagalan koneksi, timeout, atau status code 4xx/5xx.   Alasan teknis membedakan kondisi data kosong dari kondisi error: Secara teknis dan semantik proses bisnis, data kosong adalah hasil respons server yang valid (HTTP 200 OK dengan payload array kosong []), yang menandakan koneksi jaringan normal dan sistem berjalan semestinya, hanya saja belum ada transaksi pengaduan yang masuk. Sebaliknya, kondisi error menandakan kegagalan teknis pada jaringan atau server (seperti tidak ada internet, timeout, HTTP 404, atau HTTP 500) sehingga sistem tidak dapat memverifikasi ketersediaan data. Menyamakan keduanya akan menyesatkan pengguna: pengguna bisa mengira server sedang rusak padahal daftar laporan memang kosong, atau mengira tidak ada laporan kerusakan padahal koneksi internetnya sedang terputus.
